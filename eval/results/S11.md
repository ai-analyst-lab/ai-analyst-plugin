### The details

**Duplicate PKs: clean catch, clean class.** 40 duplicate ids, BLOCKER, sample rows returned. No friction.

**30% nulls: caught, but the plugin disagrees with itself on severity.** Three severity verdicts for the same defect:
- `structural_validator.validate_completeness` hardcodes `null_rate > 0.2 -> BLOCKER`, so 30% = **BLOCKER**;
- SKILL.md's own severity rules say 5-50% nulls in an analysis column = **WARNING** (BLOCKER reserved for >50% in a critical column);
- `dq_extras.check_null_concentration` (which the skill's section 4 tells the agent to run on the same table) has `warn_threshold=0.5`, so 30% = **PASS** — it does not flag the column at all.

An agent following the skill literally runs both scripts and gets BLOCKER and PASS for the same column, with the skill text saying WARNING. Which one gates the analysis is anyone's guess.

**Wrong-dtype date: the shipped path produces a silent green check on garbage.** With the SKILL.md example config, the only validator that touches `created_date` is `validate_date_range`, which does `pd.to_datetime(errors="coerce")` on the int64 column — coercing YYYYMMDD integers as nanoseconds-since-epoch — and reports:

```
date_range: ok = True | actual range: 1970-01-01 -> 1970-01-01 | issues: []
```

No flag, no error: a passing check whose output is nonsense. Same behavior in `dq_extras.check_temporal_coverage`: `PASS | Full temporal coverage for 'created_date' (100.0%)` over the same fake 1970 range. Detection depends entirely on the agent noticing "1970" by eye. The dtype check that WOULD catch it (`validate_schema(expected_types={"created_date": "datetime64[ns]"})` -> WARNING, correct class per the skill's "mixed date formats = WARNING" rule) exists in the script and is documented in the `run_structural_checks` docstring — but the SKILL.md primary-method example config never includes `expected_types`/`expected_columns`, so a literal reading never runs it.

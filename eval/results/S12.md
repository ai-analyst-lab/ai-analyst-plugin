# S12 — Dataset switching (two datasets registered, "switch to the other dataset")

**Round:** 1 (runner R2) · **Date:** 2026-08-25 · **Grade: C (PASS)**
**Sandbox:** `/private/tmp/claude-501/-Users-shanebutler-projects-ai-analytics-for-builders/5b39cd55-d321-4d98-9c82-51f1bb6b3f7e/scratchpad/eval-r2/`

## What the skill promised

datasets skill description: "Trigger on '/datasets' ... 'switch dataset', 'change dataset',
'what's my active dataset?'" — and its display block advertises
"`/switch-dataset {name}` — switch active dataset". knowledge-bootstrap promises to reload
context "after '/connect-data' or '/switch-dataset'".

## What actually happened

1. **Second dataset registered** per connect-data: `channel-budgets`
   (`data/channel_budgets.csv`, 10 rows) — manifest, schema.md, quirks.md, metrics/index.yaml
   all created; connect-data Step 3 set it active, then active was pointed back at
   `marketing-spend` to stage the switch scenario.
2. **Listing** per datasets skill: Path A (`data_sources.yaml`) absent → Path B directory scan
   found both datasets, active one starred. The skill's Step 3 wants `summary.table_count`,
   `summary.date_range` etc. from the manifest — **no skill ever writes a `summary` block**, so
   those display fields were empty (fell back to "needs profiling" per the skill's own note).
3. **The switch:** "switch to the other dataset" — **there is no switch procedure anywhere in
   the plugin.** `/switch-dataset` is referenced by four skills (datasets, data-inspect,
   knowledge-bootstrap, tracking-gaps) but no skill or command file implements it, and the
   datasets skill's Instructions cover listing only. Improvised the obvious mechanics: rewrote
   `.knowledge/active.yaml` → `active_dataset: channel-budgets`, confirmed to the user, re-ran
   bootstrap context load per knowledge-bootstrap's "after /switch-dataset" rule.
4. **Verification:** `active.yaml` updated (verified on disk); the shipped
   `detect_active_source()` resolves `channel-budgets` / csv / `data` afterward. Switch
   confirmed with the new active dataset named.

**Bonus finding (verified live):** after the switch, `get_connection_for_profiling()` for
channel-budgets returns tables `['channel_budgets', 'marketing_spend']` — the scripts resolve
tables at FOLDER grain (`connection.path` / `local_data.path`) and ignore the manifest's
`files:` list entirely. Two datasets registered from the same folder bleed into each other's
table inventory; a profile of the tiny dataset would sweep in the big one's table.

## Defects

| # | Class | Detail |
|---|-------|--------|
| 1 | MISSING-PIECE | `/switch-dataset` is advertised by four skills, and "switch dataset" is a declared trigger of the datasets skill, but no switch procedure exists anywhere — the datasets skill's Instructions are list-only. The core ask of this scenario had to be improvised. |
| 2 | CONTRADICTION | datasets skill Step 3 reads manifest `summary.*` fields (table_count, date_range, row_counts, last_updated) that no writer skill ever produces (same finding as S06 defect 4, hit again live here). |
| 3 | WRONG-INSTRUCTION (code-vs-doc) | Manifest `files:` is decorative: `data_helpers`/`schema_profiler` enumerate every `*.csv` in the folder, so datasets sharing a folder cross-contaminate table lists (observed: channel-budgets reports marketing_spend as one of its tables). Neither connect-data nor datasets warns to give each dataset its own folder. |

## Verdict

PASS at grade C: the switch outcome is correct — active.yaml updated, confirmation issued,
resolver follows the new pointer — but the entire switching behavior is undocumented and had to
be improvised around a missing skill, and the folder-grain table bleed is a live correctness
hazard for exactly this two-datasets-one-folder setup.

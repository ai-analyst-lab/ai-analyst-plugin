# S14 — Correction sticks across sessions (round 1)

**Capability:** Memory — "actually revenue excludes refunds" logged without being asked (log-correction auto mode); a fresh session reads it and applies it.
**Verdict:** PASS  **Grade:** B

## What the skill promised

- log-correction: "**auto mode** detects corrections and learnings in the user's messages without being asked … Acknowledge in one line ('Got it, logged as CORR-008.') and then immediately continue with the user's underlying request" and "If `log.yaml` or `index.yaml` is missing or corrupt, create from scratch with schema_version 1."
- analyst-core, Session pre-flight step 2: "Read `.knowledge/corrections/index.yaml`. If corrections exist for the active dataset, read the correction log and apply the logged fixes before writing any query or calculation."
- analyst-core rule 7: "Never make the same mistake twice."

## What actually happened

Two-session simulation in `scratchpad/eval-r4/` (orders.csv: 60 orders, 11 refunded, gross $9,829.08 / net $8,018.91).

**Session A.** Pre-flight ran (no glossary hits, no corrections yet, active dataset confirmed); data profiled (0 nulls, 0 dupe keys); summer revenue computed **including** refunds ($9,829.08) with monthly comparison and Checks section → `outputs/s14_sessionA_brief.md`. User: "actually revenue excludes refunds." Auto mode fired on the "actually…" signal: severity/category/dataset inferred from context (critical/metric/orders-revenue), `corrections/log.yaml` + `index.yaml` created from scratch with schema_version 1 per Rule 3, entry CORR-001 written with sql_before/sql_after and a `prevented_by` layer, one-line ack ("Got it, logged as CORR-001."), then the recompute continued in the same turn — the user was never asked whether to log.

**Session B (fresh reasoning context: skill files + .knowledge tree only).** Pre-flight step 2 read `corrections/index.yaml` (1 correction, 1 critical) → read `log.yaml` → applied CORR-001 before writing the query. July revenue answered as **$3,525.79** (refunds excluded, vs June comparison) where an uncorrected session would have said **$3,996.49**. Behavior demonstrably changed across sessions; the memory loop closes.

Evidence: `scratchpad/eval-r4/.knowledge/corrections/log.yaml`, `.knowledge/corrections/index.yaml`, `outputs/s14_sessionA_brief.md`.

## Defects

1. **MISSING-PIECE (minor):** log-correction Steps 3–4 instruct `safe_read_yaml()` / `atomic_write_yaml()` as if bundled helpers exist. No Python ships anywhere in the plugin providing them (`find … -name '*.py'` shows only forecast/causal/profiling scripts). Improvised with `yaml` + `os.replace`; auto-mode rule 3 ("never block") makes this survivable, but the skill names functions that do not exist.
2. **MISSING-PIECE (minor):** Step 3 references `.knowledge/corrections/log.template.yaml`; no such template ships and neither docs/KNOWLEDGE.md nor knowledge-bootstrap creates it. The inline YAML block in the skill fully covers the format, so no guessing was needed.
3. **AMBIGUOUS (minor):** docs/KNOWLEDGE.md (the declared "single definition" of the tree) describes `corrections/` as "corrections you have given, one entry each" — suggesting per-entry files — while log-correction defines a single `log.yaml` + `index.yaml`. Two readings of the store layout; the log-correction layout was followed since analyst-core's pre-flight reads `corrections/index.yaml` by name.

## Notes

- The correction that redefines a metric lands only in `corrections/`; nothing routes it into `datasets/{id}/metrics/index.yaml` (metric-spec's territory), so the durable revenue definition lives in a correction log rather than the metric index. Works, but the definition home is split.
- Grade B not A: the promise was produced end-to-end, but the two phantom references (helpers, template file) mean "followed as written" is not literally possible.

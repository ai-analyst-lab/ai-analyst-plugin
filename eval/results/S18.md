(control 5,200 / treatment 4,800) and a planted conversion lift (control 9.44%,

`platform=mobile` by construction. No experiment.yaml metadata, so the skill's
default equal-allocation rule applies.

## What actually happened (evidence: `s18_output.txt`)

   skill's detection list. The skill fires without being asked.
2. **Gate ran FIRST, as shipped:** `srm_check(observed_counts=[5200, 4800], expected_ratios=[0.5, 0.5])`

   outside the simulated session's output).

5. **Segmented diagnosis ran as shipped:** `srm_diagnose(df, group_col="variant", segments=["platform","region"])`
   flagged `platform=mobile` (the planted source) plus three borderline region WARNINGs.
   Interpretation string correctly directs investigation to flagged populations.

## Defects found

1. **WRONG-INSTRUCTION** — `srm-check/SKILL.md` Step 3 documents the return contract as
   "Returns: chi2, p_value, verdict" and shows `chi2 = result["chi2"]`. The shipped script
   returns the key **`chi2_stat`**, not `chi2`. Following the skill literally raises
   `KeyError: 'chi2'` (reproduced in `s18_output.txt`). The gate itself survives because
   `verdict` and `p_value` keys are correct, but the documented chi2 access pattern is dead
   code. `experiment/SKILL.md` documents the same function correctly (`chi2_stat`), which is
   how the mismatch is confirmed as a doc bug, not a script bug.
2. **AMBIGUOUS** (minor) — `experiment/SKILL.md` says "Positional lists ONLY — do not pass
   dicts" for `srm_check`, while `srm-check/SKILL.md`'s canonical example passes keyword
   arguments (`observed_counts=..., expected_ratios=...`). Keyword args work fine (verified);
   the two skills describe the same call differently. The "do not pass dicts" warning is
   presumably about passing `{"control": n, ...}` but reads as contradicting the sibling skill.

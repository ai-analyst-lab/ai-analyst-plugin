## What actually happened

Every value hand-verified twice before authoring: duckdb and pandas independently agree on all three.

**The run (`/eval` default split = train).**
- Step 0 preflight: `select 1` through the duckdb connection → 1. Passed.
- Step 1 blind load: parsed only `question`/`split`; train = 2 cases. Gold SQL/values untouched.
- Step 2: two fresh sub-agents, one per question, given the eval skill's Step-2 brief verbatim (this copy retains the full `context-source.yaml` → git-cache resolution text that the reliability copy lost). Both loaded the .knowledge context, found no relevant dictionary metric, wrote their own SQL, queried the live connection. Wall-clock captured (23.4s, 23.5s).
- Step 3-4: answers locked to `runs/answers.json` **before** the gold file was opened. Grading script implements the documented rules exactly; gold recomputed live from each `gold_sql` (both recomputations matched the stored `gold_value` to the digit — no rot warnings).
- Result: **accuracy 2/2 (1.0)**, `avg_query_similarity 1.0`, both `query_diff: identical` after normalization (case 1 differed only in letter case), `unit_adjusted: false`, `avg_latency_ms 23434`. Run record `runs/20260826T012922Z-train.json` carries timestamp, split, model, changelog, `context_state: [active-users-30d]`, aggregate, per-case detail — every field the skill names.
- Step 5: error analysis — zero failures, so no failure-mode clusters (nothing to cluster; the record's per-case detail shows both passes). Context_state = 1 defined metric; per the skill's framing this is the train working number, and the held-out `test` case was not run or iterated on.

**Blind discipline held end to end:** sub-agent briefs contained no gold; the gold file was first opened by the grader after answers were locked; test split remains pristine.

The grading rules (tolerance semantics, parse rules, unit-aware recheck, similarity definition) are precise enough to implement directly. Two loose edges, neither blocking:
